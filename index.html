// how i build

AI is my collaborator — judgment is my job

I'll be upfront: I built the regime identifier and this site with AI agents as collaborators, and learning to direct AI well is something I practise deliberately. My part is the judgment — choosing the problem, deciding what would prove the system wrong, and refusing to ship anything I can't explain. The quotes below come straight from my own development session logs.

"test me after every lesson"

Before starting the real project, I ran a separate learning repo and told the AI to quiz me after every lesson and explain the hardest lines of code — OHLCV structure, why columnar storage beats rows, how to handle API rate limits. I wanted the concepts in my own head before any system got built.

"help me fully understand the project"

I set up a review agent, Adam, whose only job is to re-read the entire repo and regenerate UNDERSTANDING.md — a plain-English map of every model, formula, and design decision, tied back to the code. My rule: if I can't explain it, it doesn't ship.

"how do i deny your access to that file"

Once live API keys entered the project, I moved the secrets outside the repo, set up hooks so even the AI couldn't read the key file, and ran a test to confirm it worked. Security boundaries apply to every collaborator, human or not.

"i'm not sure the plan is relevant — help me evaluate it"

I don't take one AI's word for anything. An architecture plan from one model got picked apart critically before any of it was adopted, and I stop agent runs that burn time without teaching me anything.

Code that runs is cheap now. Knowing what to build, what would prove it wrong, and whether to trust the output is not — and that's the part I keep working on.

// featured project

Market Regime Identifier

A Python research system built around a simple-sounding question: “what kind of market are we in right now — and can you trade that answer honestly?”

A 4-state Gaussian Hidden Markov Model reads three daily features from index prices (log return, 21-day realized volatility, 63-day trend) and discovers four recurring regimes on its own: quiet_bull, volatile_bull, sideways, volatile_bear. Detecting them was the easy half. Most of the project is the machinery that checks whether those labels are real and tradeable — not just pretty in hindsight.

01 / the model

Gaussian HMM over daily features, with BIC-based selection to justify the state count instead of guessing it, and state-ranking logic that survives HMM label switching between fits.

02 / no lookahead

Walk-forward validation refits the model yearly on an expanding window and labels each year strictly out-of-sample with causal (filtered) probabilities. Macro features are point-in-time aligned with release lags, so backtests never see data before it was published.

03 / strategy layer

Per-regime trading rules evolved with genetic programming (gplearn) on a block-bootstrap synthetic episode corpus, scored across many seeds on holdout Sharpe net of turnover costs — judged by the fraction of seeds that beat the baseline, not one lucky seed.

04 / true out-of-sample

Rules trained on SPY are tested unchanged on QQQ, and the full composite strategy is backtested on DIA — a ticker whose data never touched training. The gap between holdout and composite numbers is treated as the honest signal, not hidden.

05 / data engineering

A provider seam swaps Yahoo daily data for Alpaca intraday bars; feature families (SPY↔QQQ divergence, FRED macro series) compose onto the base model; prices are cached and every intraday bar is tagged to its regime episode.

06 / engineering practice

Packaged as an installable Python library with a pytest suite, GitHub Actions CI, and self-contained interactive HTML dashboards (Plotly) that work offline.

What this project taught me about honest research

  • Exploratory charts that label history with a full-history fit can effectively see the future — the README documents this lookahead bias instead of hiding it.
  • Gaussian emissions understate fat tails, and regime durations are geometric (right-skewed), not normal.
  • A strategy that “wins” on one seed means nothing. A strategy that beats always-long on every seed in volatile_bear means something.
  • The composite backtest inherits every real-world seam at once — misclassification, late transitions, warm-up gaps — so it is expected to look worse than the per-regime numbers. That gap is information.

SinoVision — Project Engineer Intern

I interned at SinoVision, working on enterprise-scale building management and access control systems across two deployments: the smart-building network infrastructure of a large mixed-use development, and an access control & visitor management system (ACVAS) for a club facility.

note: everything on this page is generalized. The diagram below shows a representative enterprise campus architecture built entirely from standard, publicly documented networking concepts — no client-specific configurations, identifiers, or layouts are disclosed.

Project 1 — smart building network

A multi-storey smart building where a central server room feeds every floor over a GPON fibre backbone, and each floor's distribution room serves access control, data, and CCTV systems on segregated VLANs. What I did on this network

  • Configured and troubleshot facial recognition access scanners — tracing controllers, locating switch ports, setting Wiegand-34 protocol parameters, and syncing devices to a central NTP server so access logs and CCTV timestamps stay aligned.
  • Worked with tagged vs untagged VLAN port configuration: trunk ports carrying multiple VLANs between switches, untagged ports for end devices like cameras and scanners that don't understand VLAN tags.
  • Troubleshot fibre optic links between distribution rooms and the server room — identifying wrong connector types (SC vs LC) and verifying links through switch indicators before touching anything at higher layers.
  • Observed static routing on the management VLAN and learned why isolated VLANs still need controlled Layer-3 paths between them.
  • Built a systematic troubleshooting habit: physical layer → link indicators → VLAN config → IP connectivity → backend communication → time sync. In that order, every time.

Project 2 — Access Control & Visitor Management System (ACVAS)

system

Visitor management for a club facility: mobile portal, admin portal, cloud-hosted backend services and SQL database, facial recognition and QR validation services.

what I learned

Physical access devices lean heavily on backend APIs — ticket creation, QR generation and validation, face verification, user sync. Hardware and software are one system, not two.

performance testing

Got introduced to Apache JMeter for benchmark and stress testing: simulating concurrent users and monitoring response times, CPU/memory utilization, and failure rates under load.
